01 · ธนาคารเลือด (Blood Bank / BBIS)

โมดูลนี้ทำหน้าที่เป็น “ตัวกลาง” ระหว่างงานตรวจรักษา (OPD/IPD) กับระบบ BBIS/LIS ของธนาคารเลือด HA.OS ไม่ได้ทำ Cross-match เอง แต่เก็บใบสั่ง (Order Confirm) ไว้ให้ LIS มาดึงผ่าน API แล้วรับผล Cross-match และการจ่ายถุงเลือดกลับมาบันทึกเป็นผล Lab + ค่าใช้จ่ายในระบบการเงิน

สิ่งที่ต้องตั้งค่าก่อนใช้งาน (Prerequisite)

ถ้า 3 ข้อนี้ไม่ครบ ระบบจะไม่สร้างใบสั่งธนาคารเลือดเลย และหน้าจอ Dashboard จะว่างเปล่า ซึ่งเป็นสาเหตุอันดับหนึ่งที่ทดสอบแล้ว “ไม่เห็นเคส”

  1. เปิด Flag ระดับโรงพยาบาล

    ตาราง TBM_HOSP_PARAMETERS คอลัมน์ IsBloodBankEnabled = 1 (เพิ่มมาโดย migration 25690528070917_AddBloodBankAndDrugCenterFlagsToHospParameters) ตั้งค่าได้จากเมนู งานผู้ดูแลระบบ › กำหนด Parameter

    โค้ดอ้างอิง: FinanceService.cs — if (!hospParam.IsBloodBankEnabled) { continue; }

  2. รหัสค่าใช้จ่าย (Expense) ต้องอยู่ในกลุ่ม Lab รหัส 01

    ตาราง TBM_EXPENSES คอลัมน์ LABGROUP = '01' เท่านั้น จึงจะถูกดักไปสร้างใบสั่งธนาคารเลือด (ตั้งค่าที่เมนู รหัส Lab / รหัสค่าใช้จ่าย)

    โค้ดอ้างอิง: if (string.IsNullOrEmpty(expense.Labgroup) || expense.Labgroup != "01") { continue; }

  3. รหัส Lab ต้องมีใน TBM_LAB_TESTS ที่คู่กับ ExpenseId เดียวกัน

    ตอน LIS ส่งผล Cross-match กลับมา ระบบจะค้น TBM_LAB_TESTS ด้วยเงื่อนไข Code = testcode และ ExpenseId = ExpenseId ของ order item ถ้าหาไม่เจอ ผลจะถูกบันทึกใน BBIS แต่จะไม่ขึ้นเป็นผล Lab ในระบบ HIS

ตรวจสอบเร็ว ๆ 
-- 1) Flag เปิดหรือยัง
SELECT IsBloodBankEnabled, BbReqPath FROM TBM_HOSP_PARAMETERS;

-- 2) มี Expense ที่เข้าเงื่อนไขธนาคารเลือดกี่รายการ
SELECT EXPENSE_ID, CODE, NAME, LABGROUP, LAB_MEANING
FROM   TBM_EXPENSES WHERE LABGROUP = '01';

-- 3) Expense เหล่านั้นมี LAB_TEST คู่กันครบไหม
SELECT e.CODE, e.NAME, t.TEST_ID
FROM   TBM_EXPENSES e
LEFT JOIN TBM_LAB_TESTS t ON t.EXPENSE_ID = e.EXPENSE_ID AND t.CODE = e.CODE
WHERE  e.LABGROUP = '01';

ภาพรวม Flow

  • 1. สั่ง LabOPD/IPD/Ward
  • 2. Order ConfirmPENDING
  • 3. Issue BloodCONFIRMED
  • 4. LIS ดึง Order→ APPROVED
  • 5. ส่งผล X-matchผล Lab
  • 6. แจ้งจ่ายถุง+ ค่าใช้จ่าย
  • 7. ตรวจสอบผลCOMPLETED

ฝั่ง HA.OS ทำอะไร

  • ดักรายการ Lab กลุ่ม 01 ตอนบันทึก Order → สร้างใบสั่งธนาคารเลือด
  • ให้เจ้าหน้าที่ยืนยัน Priority + วันที่ใช้เลือด แล้ว Submit
  • เปิด API ให้ LIS ดึงและส่งผลกลับ (auth ด้วย PersonalToken)
  • แปลงผล/การจ่ายถุงเลือด → TB_LAB_RESULTS + TB_FINANCES

ฝั่ง LIS/BBIS ทำอะไร

  • Poll GET /api/BloodBank/orders/{orderNumber} ตามเลข Order
  • ทำ Cross-match แล้ว POST /api/BloodBank/cross-matches
  • จ่ายถุงเลือดแล้ว POST /api/BloodBank/blood-issues

ทั้ง 3 endpoint อยู่ใต้ BloodBankApiServiceController ซึ่งใช้ [CustomApiServiceAuthorize] — ต้องส่ง header PersonalToken

ขั้นที่ 1 — เกิด Order จากงานตรวจรักษา

ผู้สั่ง Lab (แพทย์ห้องตรวจ / พยาบาล Ward / งานการเงิน–บันทึกค่าใช้จ่ายที่ไม่ใช่ยา) บันทึกรายการ Lab ที่อยู่ในกลุ่มธนาคารเลือด ระบบจะทำงานใน FinanceService ดังนี้

  1. สร้างแถวการเงินตามปกติ

    เขียน TB_FINANCES 1 แถวต่อ 1 รายการ Lab (มี ORDER_ID ร่วมกันทั้งใบสั่ง)

  2. ตรวจ Flag + Labgroup

    ถ้า IsBloodBankEnabled เป็นเท็จ หรือ Expense.Labgroup != '01' → ข้าม ไม่สร้าง BBIS

  3. สร้าง / ใช้ซ้ำ ใบสั่งธนาคารเลือด

    ค้น TB_BBIS_ORDER_CONFIRM ด้วย OrderNumber = TB_FINANCES.ORDER_ID ถ้ายังไม่มีก็สร้างใหม่ พร้อม snapshot ข้อมูลผู้ป่วย (HN, AN, VN, ชื่อ-สกุล, เพศ, วันเกิด, สิทธิ, Ward) และตั้ง ConfirmStatus = PENDING

    หมายเหตุ: 1 ใบสั่ง (OrderId) = 1 แถว Order Confirm และมีได้หลาย Item

  4. เพิ่มรายการ Item

    เขียน TB_BBIS_ORDER_CONFIRM_ITEM โดยคัดลอกทั้งข้อมูล Lab (TestCode/TestName/Qty/Volume) และข้อมูลเงิน (Price, Amount, Claim, Copay, Discount, Payment, Reminburse, Cost) จาก TB_FINANCES

  5. (กรณี Auto Accept) ยิงไฟล์ให้ LIS แบบเดิม

    ถ้า Expense.LabMeaning = 'BB' ระบบจะเรียก MlabService.BloodBankRequest(orderId) ซึ่งเขียนไฟล์ ASTM {OrderId}.bld ลง path TBM_HOSP_PARAMETERS.BbReqPath (ดู ช่องทาง Legacy)

แยกให้ชัด

LABGROUP = '01' คุมการสร้าง ใบสั่งใน BBIS ใหม่ (ตาราง TB_BBIS_*) ส่วน LAB_MEANING = 'BB' คุมการเขียน ไฟล์ ASTM แบบเดิม — เป็นคนละเส้นทาง ในการทดสอบ Flow ใหม่ให้สนใจ LABGROUP เป็นหลัก

ขั้นที่ 2 — หน้า “รายชื่อผู้ป่วยตรวจ Lab”

เส้นทาง: /blood-bank/dashboard · Component BloodBankDashboardComponent

  1. เข้าเมนู 12.2

    Sidebar เปลี่ยนเป็นเมนูย่อยของธนาคารเลือด: “รายชื่อผู้ป่วยตรวจ Lab” และ “ตรวจสอบผล Lab”

  2. ระบบโหลดรายการของ “วันที่” ที่เลือก

    POST /api/BloodBank/orders ด้วย body { orderDate, orderId?, hn?, an?, status? } ค่าเริ่มต้นคือวันนี้ (ช่วง 00:00:00 – 23:59:59 ของ ORDER_DATE_TIME)

  3. อ่านการ์ดสรุปด้านบน

    ระบบคืนตัวนับมาให้กดกรองได้ทันที

    ฟิลด์ความหมายเงื่อนไข
    Totalใบสั่งทั้งหมดของวัน—
    PendingTotalรอยืนยันPENDING
    ConfirmedTotalยืนยันแล้ว รอ LIS ดึงCONFIRMED
    ApproveTotalLIS ดึงไปแล้วAPPROVED
    EmergencyTotalจำนวน Item ที่ด่วนPriority = STAT หรือ PRE_OPERATION
    NormalTotalจำนวน Item ปกติPriority = ROUTINE
    OpdTotal / IpdtTotalแยก OPD / IPDOpdIpd = 'O' / 'I'
  4. ค้นหา

    ช่อง Order No. / HN / AN — ค้น Order No. เป็นการกรองฝั่ง Client (filterOrderId()) ส่วนการกดกรองสถานะจะยิง API ใหม่ทุกครั้ง

  5. คลิกเลือกผู้ป่วย 1 ราย

    GET /api/BloodBank/orders/{orderNumber}/items → แสดงรายละเอียดผู้ป่วย (รูป, อายุ, สิทธิ, เบอร์โทร) และรายการ Lab ที่ จัดกลุ่มตาม Lab Group (join TBM_LAB_GROUPS ผ่าน TBM_EXPENSES.LABGROUP) พร้อมยอดเงินรายบรรทัด

ขั้นที่ 3 — Issue Blood & Submit

เป็นขั้นที่เจ้าหน้าที่ธนาคารเลือด “ยืนยันใบสั่ง” ก่อนปล่อยให้ LIS ดึงไปทำงาน

  1. กดปุ่ม Issue Blood

    GET /api/BloodBank/orders/{orderNumber}/issue → หน้าจอเปลี่ยนเป็น pageState = 'issue-blood' พร้อมสร้างฟอร์ม (FormArray) 1 แถวต่อ 1 Item

  2. กำหนด Priority และวันที่ใช้เลือด รายบรรทัด
    ตัวเลือกบนจอค่าที่บันทึกผลต่อการแสดงผล
    RoutineROUTINEเข้ากลุ่ม “ปกติ” (issueItemsRoutine)
    STATSTATเข้ากลุ่ม “ด่วน” (issueItemsUrgent)
    Pre-operationPRE_OPERATIONเข้ากลุ่ม “ด่วน”

    ทั้ง useDate และ priority เป็น required ทั้งคู่ในฟอร์ม

  3. กดบันทึก (ยังไม่ Submit)

    PUT /api/BloodBank/orders/{orderNumber}/issue — อัปเดต Priority, UseDate และประทับ UserModified / DateModified

    พฤติกรรมที่ต้องรู้

    UpdateOrderConfirmItems จะ ลบ Item ที่ไม่ได้ส่งมาใน request ทิ้ง (itemsToRemove = item ที่ Code ไม่อยู่ใน request) ดังนั้นการเรียก API นี้เองต้องส่ง Item ครบทุกบรรทัดเสมอ มิฉะนั้นรายการที่หายไปจะถูกลบออกจากใบสั่ง

  4. ติ๊กยืนยัน แล้วกด Submit

    หน้าจอบังคับติ๊ก confirmChecked ก่อน (กล่อง showConfirmBBIS) จากนั้น POST /api/BloodBank/orders/{orderNumber}/submit

    ผลที่เกิดขึ้นใน DB:

    ตารางคอลัมน์ค่าใหม่
    TB_BBIS_ORDER_CONFIRMConfirmStatusCONFIRMED
    OrderStatusINPROGRESS
    TB_BBIS_ORDER_CONFIRM_ITEM
    (ทุกแถว)    		ItemStatusPENDING (สถานะผล X-match)
    IssueStatusPENDING (สถานะจ่ายถุงเลือด)

    Submit ซ้ำจะถูกปฏิเสธ — โค้ดเช็ค if (bbisOrder.ConfirmStatus == CONFIRMED) return Fail

ขั้นที่ 4-6 — ฝั่ง LIS / BBIS

ขั้นที่ 4 — LIS ดึงใบสั่ง

GET /api/BloodBank/orders/{orderNumber}

  • รับเฉพาะใบสั่งที่ ConfirmStatus ∈ {CONFIRMED, APPROVED} เท่านั้น — ถ้ายัง PENDING จะได้ OrderNumber not found.
  • ถ้าเป็น CONFIRMED ระบบจะ เปลี่ยนเป็น APPROVED ทันทีที่ถูกอ่าน (ถือว่า LIS รับงานไปแล้ว) — เป็น side-effect ของ GET ที่ต้องระวังตอนทดสอบ
  • คืนข้อมูลผู้ป่วย + array order[] (testcode, testname, qty, volume, priority, usedate)

ขั้นที่ 5 — LIS ส่งผล Cross-match

POST /api/BloodBank/cross-matches

  1. ตรวจสิทธิ์เข้าถึงใบสั่ง

    ต้อง ConfirmStatus = APPROVED เท่านั้น

  2. จับคู่ Item ด้วย testcode

    เทียบกับ TB_BBIS_ORDER_CONFIRM_ITEM.TestCode ถ้าไม่ตรง → ข้ามเงียบ ๆ

  3. บันทึกผล

    เพิ่มแถว TB_BBIS_RESULT (ResultText, BagNumber, Component, ApproveBy, ApproveDateTime) และตั้ง Item.ItemStatus = COMPLETED

  4. สร้างผล Lab ในระบบ HIS

    ถ้าหา TBM_LAB_TESTS และ TB_FINANCES ที่ผูกกันเจอ จะเพิ่มแถว TB_LAB_RESULTS แล้วเขียน LabResultId กลับไปที่ TB_BBIS_RESULT

  5. อัปเดตสถานะใบสั่ง

    OrderStatus = INPROGRESS และจะเป็น COMPLETED เมื่อ ทุก Item มี ItemStatus = COMPLETED

ขั้นที่ 6 — LIS แจ้งจ่ายถุงเลือด

POST /api/BloodBank/blood-issues — เป็นขั้นที่ เกิดค่าใช้จ่ายจริง

  1. ตรวจ ConfirmStatus = APPROVED และเปิด DB Transaction ครอบทั้งงาน
  2. โหลดบริบทล่วงหน้า

    ผู้ป่วย, TBM_EXPENSES, และบริบท OPD (TB_OPD_SERVICES/TB_OPD_CLINICS/TB_OPD_RIGHTS) หรือ IPD (TB_ADMITS/TB_ADMIT_RIGHTS) ตาม OpdIpd

  3. กันการส่งซ้ำ

    สร้าง key (BbisOrderConfirmItemId, BagNumber) จากแถวที่เคย issue แล้ว ถ้าซ้ำ → ข้าม ไม่สร้างค่าใช้จ่ายซ้ำ (รองรับ retry ของ LIS)

  4. เขียน TB_BBIS_ISSUE + TB_FINANCES

    ค่าใช้จ่ายทุกแถวที่เกิดในการ submit รอบเดียวกันจะใช้ OrderId เดียวกัน (จาก SequenceHelper.GetSequenceNumber(SeqGenerateFinanceOrderId)) และตั้ง Item.IssueStatus = COMPLETED

    ค่า FinanceType มาจาก Expense.FinanceType ถ้าไม่มีจะใช้ 'L' (LAB) ส่วน UserDispensed/DateDispensed มาจาก issueby/issuedate ที่ LIS ส่งมา

  5. เขียน FinanceId กลับ

    บันทึก Item.FinanceId (เก็บค่าแรกเท่านั้น หากมีหลายถุงต่อ 1 Item) ถ้าเกิดข้อผิดพลาดกลางทาง จะ Rollback ทั้งชุด

ลำดับสำคัญมาก

TB_LAB_RESULTS ในขั้นที่ 5 ต้องอาศัย Item.FinanceId ซึ่งถูกเซ็ตในขั้นที่ 6 ดังนั้นถ้ายิง cross-matches ก่อน blood-issues ระบบจะบันทึก TB_BBIS_RESULT ให้ แต่ จะไม่สร้าง TB_LAB_RESULTS (โค้ด if (labTest == null || finance == null) continue;) → ผล Lab จะไม่ไปโผล่ในระบบ HIS ปกติ

ลำดับที่แนะนำสำหรับการจำลอง: GET order → blood-issues → cross-matches

ขั้นที่ 7 — หน้า “ตรวจสอบผล Lab”

เส้นทาง: /blood-bank/lab-result · Component LabResultCheckComponent

  1. เลือกวันที่ / ค้นหา

    POST /api/BloodBank/orders/search-results — แสดงเฉพาะใบสั่งที่ ConfirmStatus = APPROVED (ยังไม่ถูก LIS ดึง จะไม่ปรากฏในหน้านี้) พร้อมตัวนับ InProgressTotal / CompleteTotal ซึ่งนับจาก OrderStatus

  2. คลิกใบสั่งเพื่อดูรายละเอียด

    GET /api/BloodBank/orders/{orderNumber}/results คืนข้อมูลสรุป 6 ตัว:

    ฟิลด์นับจาก
    AllResultTotal / ResultPendingTotal / ResultCompletedTotalItem.ItemStatus (ผล Cross-match)
    AllIssueTotal / IssuePendingTotal / IssueCompletedTotalItem.IssueStatus (การจ่ายถุงเลือด)

    ตารางรายบรรทัดแสดง: กลุ่ม Lab, Priority, ผล (ResultText), ผู้ Approve + เวลา, สถานะจ่าย, เลขถุง/ส่วนประกอบ, ผู้จ่าย + เวลา

  3. พิมพ์ใบรับเลือด

    ปุ่มพิมพ์เรียก PrintReportService.exportReportPdf_BloodReceive(orderNumber)

State Machine

ระดับใบสั่ง — ConfirmStatus (สถานะการยืนยัน)

  • PENDINGเกิดจากการสั่ง Lab
  • CONFIRMEDจนท. กด Submit
  • APPROVEDLIS เรียก GET order

ระดับใบสั่ง — OrderStatus (สถานะงานผล)

  • INPROGRESSตั้งตอน Submit / รับผลบางส่วน
  • COMPLETEDทุก Item มี ItemStatus = COMPLETED

ระดับรายการ — ItemStatus และ IssueStatus

คอลัมน์PENDINGCOMPLETEDถูกเปลี่ยนโดย
ItemStatusรอผล Cross-matchได้ผลแล้วPOST /cross-matches
IssueStatusยังไม่จ่ายถุงเลือดจ่ายแล้ว + ลงค่าใช้จ่ายแล้วPOST /blood-issues

ค่าคงที่ทั้งหมดอยู่ที่ BloodBankOrderStatus / BloodBankItemStatus — PENDING, INPROGRESS, CONFIRMED, APPROVED, COMPLETED และ ROUTINE, STAT, PRE_OPERATION

ตารางฐานข้อมูล

ตารางหน้าที่คอลัมน์สำคัญ
TB_BBIS_ORDER_CONFIRM หัวใบสั่ง 1 แถวต่อ 1 OrderId BbisOrderConfirmId (PK), OrderNumber = TB_FINANCES.ORDER_ID, PatientId, HN, AN, VN, OpdIpd, RightId, WardCode, OrderDateTime, ConfirmStatus, OrderStatus
TB_BBIS_ORDER_CONFIRM_ITEM รายการ Lab + ยอดเงิน ExpenseId, TestCode, TestName, Qty, Volume, Priority, UseDate, Price/Amount/Claim/Copay/Discount/Payment/Reminburse/Cost, ItemStatus, IssueStatus, FinanceItemCode, FinanceId
TB_BBIS_RESULT ผล Cross-match ที่ LIS ส่งมา ResultText, BagNumber, Component, ApproveBy, ApproveDateTime, LabResultId
TB_BBIS_ISSUE ประวัติจ่ายถุงเลือด TestCode, ResultText, BagNumber, Component, IssueBy, IssueDateTime
TB_FINANCES ค่าใช้จ่าย (สร้างตอน blood-issues) FinanceType, Code, ExpenseId, OrderId, Labnumber, UserDispensed, DateDispensed
TB_LAB_RESULTS ผล Lab ในระบบ HIS ปกติ FinanceId, TestId, LabResultCode, LabOrderCode, OrderId

การจำลอง Case แทน LIS

เมื่อยังไม่มี BBIS จริงมาเชื่อม เราสามารถ “สวมบทเป็น LIS” ได้ครบทุกขั้นด้วยการยิง HTTP 3 ครั้ง ต่อไปนี้คือขั้นตอนแบบ end-to-end

A. เตรียม PersonalToken (ทำครั้งเดียว)

  1. เข้าเมนู งานผู้ดูแลระบบ › ลงทะเบียนผู้ใช้งานระบบ

    เลือกผู้ใช้ที่จะให้เป็น “บัญชีของ LIS” (แนะนำสร้าง user แยก เช่น svc_bbis เพราะทุกค่าใช้จ่ายที่เกิดจาก blood-issues จะบันทึก UserCreated เป็น user เจ้าของ token นี้)

  2. สร้าง Personal Access Token

    ตั้งชื่อ Token + วันหมดอายุ (เว้นว่าง = ไม่หมดอายุ) แล้วกดสร้าง ระบบจะเปิด dialog แสดง token ซึ่งเป็น GUID แบบไม่มีขีด 32 ตัวอักษร

    แสดงครั้งเดียว

    ระบบเก็บเฉพาะค่า hash ลง TB_PERSONAL_ACCESS_TOKENS.AccessToken ถ้าปิด dialog ไปแล้วจะดูย้อนหลังไม่ได้ ต้องกด Revoke เพื่อออกใหม่

  3. ทดสอบ token

    ยิง GET ใบสั่งใดก็ได้ — ถ้าได้ 401 แปลว่า token ผิด/หมดอายุ, ถ้าได้ 500 แปลว่าฝั่ง server มีปัญหา (เช่น DB) ไม่ใช่ token หมดอายุ

B. เตรียมเคสทดสอบใน HA.OS

  1. ตรวจ Prerequisite ครบ 3 ข้อ

    ดูหัวข้อ Prerequisite ด้านบน

  2. สั่ง Lab กลุ่มธนาคารเลือดให้ผู้ป่วยทดสอบ

    ทำผ่านห้องตรวจแพทย์ หรือทางลัดที่เร็วกว่า: งานการเงิน › บันทึกค่าใช้จ่ายที่ไม่ใช่ยา แล้วเลือกรายการ Lab ที่ LABGROUP = '01'

  3. จดเลข Order Number

    คือ TB_FINANCES.ORDER_ID ของใบสั่งนั้น หาได้จากหน้า Dashboard ธนาคารเลือด (คอลัมน์ Order No.) หรือ SQL ด้านล่าง

    SELECT TOP 20 c.ORDER_NUMBER, c.HN, c.AN, c.OPD_IPD,
       c.CONFIRM_STATUS, c.ORDER_STATUS, c.ORDER_DATE_TIME
FROM   TB_BBIS_ORDER_CONFIRM c
ORDER BY c.BBIS_ORDER_CONFIRM_ID DESC;
  4. Issue Blood + Submit บนหน้าจอ

    ต้องทำขั้นนี้ก่อนเสมอ ไม่งั้น GET ฝั่ง LIS จะไม่เห็นใบสั่ง (ยังเป็น PENDING)

  5. จดรายการ testcode ที่ต้องใช้ 
    SELECT i.TEST_CODE, i.TEST_NAME, i.EXPENSE_ID, i.QTY,
       i.PRIORITY, i.ITEM_STATUS, i.ISSUE_STATUS
FROM   TB_BBIS_ORDER_CONFIRM_ITEM i
JOIN   TB_BBIS_ORDER_CONFIRM c ON c.BBIS_ORDER_CONFIRM_ID = i.BBIS_ORDER_CONFIRM_ID
WHERE  c.ORDER_NUMBER = '<ORDER_NUMBER>';

    testcode ที่ต้องส่งกลับมา = ค่าในคอลัมน์ TEST_CODE นี้เป๊ะ ๆ (คือรหัส Expense)

C. ยิง API แทน LIS

ตัวอย่างใช้ base URL http://localhost:5000 (ค่าใน config.deploy.json ของ WebClient) แทน <TOKEN> ด้วย Personal Access Token และ <ORDER> ด้วย Order Number

C.1 — ดึงใบสั่ง (จำลอง LIS รับงาน)

# bash / curl
curl -s -X GET "http://localhost:5000/api/BloodBank/orders/<ORDER>" \
     -H "PersonalToken: <TOKEN>"
# PowerShell
$h = @{ 'PersonalToken' = '<TOKEN>' }
Invoke-RestMethod -Method Get 'http://localhost:5000/api/BloodBank/orders/<ORDER>' -Headers $h |
  ConvertTo-Json -Depth 6

ผลที่คาดหวัง: ได้ข้อมูลผู้ป่วย + order[] และสถานะใบสั่งเปลี่ยนเป็น APPROVED

C.2 — แจ้งจ่ายถุงเลือด (ทำก่อน เพื่อให้เกิด FinanceId)

curl -s -X POST "http://localhost:5000/api/BloodBank/blood-issues" \
  -H "PersonalToken: <TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{
    "ordernumber": "<ORDER>",
    "hn": "<HN>",
    "title": "นาย",
    "name": "ทดสอบ",
    "lastname": "ระบบ",
    "idcard": "1234567890123",
    "sex": "M",
    "dob": "1990-01-01",
    "issue": [
      {
        "testcode":  "<TEST_CODE>",
        "testname":  "Cross Matching",
        "itemcost":  "500",
        "result":    "Compatible",
        "bagnumber": "BAG-0001",
        "component": "LPRC",
        "issueby":   "MT001",
        "issuedate": "2026-09-08T10:30:00"
      }
    ]
  }'

ผลที่คาดหวัง:

  • เพิ่มแถวใน TB_BBIS_ISSUE
  • เพิ่มแถวใน TB_FINANCES (ค่าใช้จ่ายถุงเลือด) ผูก Labnumber = ORDER_NUMBER
  • Item.IssueStatus → COMPLETED และ Item.FinanceId ถูกเซ็ต
หลายถุงต่อ 1 รายการ

ส่งหลาย element ใน issue[] ที่มี testcode เดียวกันแต่ bagnumber ต่างกันได้ ระบบจะสร้าง TB_FINANCES แยกแถวต่อถุง แต่ Item.FinanceId จะเก็บเฉพาะแถวแรก และการส่ง bagnumber เดิมซ้ำจะถูกกันไว้ (idempotent)

D. สคริปต์จำลองครบ Flow (PowerShell)

$base  = 'http://localhost:5000'
$token = '<TOKEN>'
$order = '<ORDER>'
$hn    = '<HN>'
$code  = '<TEST_CODE>'
$h = @{ 'PersonalToken' = $token; 'Content-Type' = 'application/json' }

# 1) LIS รับงาน  (CONFIRMED -> APPROVED)
Invoke-RestMethod -Method Get "$base/api/BloodBank/orders/$order" -Headers $h

# 2) แจ้งจ่ายถุงเลือด -> เกิด TB_FINANCES + FinanceId
$issue = @{
  ordernumber = $order; hn = $hn
  issue = @(@{
    testcode  = $code;      testname  = 'Cross Matching'
    itemcost  = '500';      result    = 'Compatible'
    bagnumber = 'BAG-0001'; component = 'LPRC'
    issueby   = 'MT001';    issuedate = (Get-Date).ToString('s')
  })
} | ConvertTo-Json -Depth 5
Invoke-RestMethod -Method Post "$base/api/BloodBank/blood-issues" -Headers $h -Body $issue

# 3) ส่งผล Cross-match -> เกิด TB_BBIS_RESULT + TB_LAB_RESULTS
$res = @{
  ordernumber = $order; hn = $hn
  result = @(@{
    testcode  = $code;      testname    = 'Cross Matching'
    result    = 'Compatible'; bagnumber   = 'BAG-0001'
    component = 'LPRC';     approveby   = 'MT001'
    approvedate = (Get-Date).ToString('s')
  })
} | ConvertTo-Json -Depth 5
Invoke-RestMethod -Method Post "$base/api/BloodBank/cross-matches" -Headers $h -Body $res

E. ตรวจผลลัพธ์ใน DB

DECLARE @ord VARCHAR(20) = '<ORDER>';

-- สถานะหัวใบสั่ง
SELECT ORDER_NUMBER, CONFIRM_STATUS, ORDER_STATUS, DATE_MODIFIED
FROM   TB_BBIS_ORDER_CONFIRM WHERE ORDER_NUMBER = @ord;

-- สถานะรายบรรทัด
SELECT i.TEST_CODE, i.PRIORITY, i.ITEM_STATUS, i.ISSUE_STATUS, i.FINANCE_ID
FROM   TB_BBIS_ORDER_CONFIRM_ITEM i
JOIN   TB_BBIS_ORDER_CONFIRM c ON c.BBIS_ORDER_CONFIRM_ID = i.BBIS_ORDER_CONFIRM_ID
WHERE  c.ORDER_NUMBER = @ord;

-- ผล X-match / การจ่ายถุง
SELECT 'RESULT' src, TEST_CODE, RESULT_TEXT, BAG_NUMBER, COMPONENT,
       APPROVE_BY AS ACTOR, APPROVE_DATE_TIME AS ACTED_AT, LAB_RESULT_ID
FROM   TB_BBIS_RESULT WHERE ORDER_NUMBER = @ord
UNION ALL
SELECT 'ISSUE', TEST_CODE, RESULT_TEXT, BAG_NUMBER, COMPONENT,
       ISSUE_BY, ISSUE_DATE_TIME, NULL
FROM   TB_BBIS_ISSUE WHERE ORDER_NUMBER = @ord;

-- ค่าใช้จ่ายที่เกิดจากการจ่ายถุงเลือด
SELECT FINANCE_ID, ORDER_ID, CODE, EXPENSE_NAME, AMOUNT,
       USER_DISPENSED, DATE_DISPENSED
FROM   TB_FINANCES WHERE LABNUMBER = TRY_CONVERT(DECIMAL(20,0), @ord);

F. Reset เคสเพื่อทดสอบซ้ำ

ใช้เฉพาะฐานข้อมูลทดสอบเท่านั้น

อย่ารันบน Production — ค่าใช้จ่ายที่ลบไปมีผลต่อใบเสร็จและงานเรียกเก็บ

DECLARE @ord VARCHAR(20) = '<ORDER>';
DECLARE @id  DECIMAL(20,0) =
  (SELECT BBIS_ORDER_CONFIRM_ID FROM TB_BBIS_ORDER_CONFIRM WHERE ORDER_NUMBER = @ord);

BEGIN TRAN;
  DELETE FROM TB_BBIS_RESULT WHERE BBIS_ORDER_CONFIRM_ID = @id;
  DELETE FROM TB_BBIS_ISSUE  WHERE BBIS_ORDER_CONFIRM_ID = @id;

  UPDATE TB_BBIS_ORDER_CONFIRM_ITEM
     SET ITEM_STATUS = 'PENDING', ISSUE_STATUS = 'PENDING', FINANCE_ID = NULL
   WHERE BBIS_ORDER_CONFIRM_ID = @id;

  -- ย้อนกลับไปสถานะ "รอ LIS ดึง" เพื่อยิง GET ใหม่ได้อีกครั้ง
  UPDATE TB_BBIS_ORDER_CONFIRM
     SET CONFIRM_STATUS = 'CONFIRMED', ORDER_STATUS = 'INPROGRESS'
   WHERE BBIS_ORDER_CONFIRM_ID = @id;
-- COMMIT;  /* ตรวจผลก่อนแล้วค่อย commit */

อย่าลืมลบ TB_FINANCES / TB_LAB_RESULTS ที่เกิดขึ้นด้วย ถ้าต้องการเคสสะอาดจริง ๆ

ข้อควรระวัง / กับดัก

1. GET มี side-effect

GET /orders/{no} เปลี่ยนสถานะจาก CONFIRMED → APPROVED เพราะฉะนั้นการ “เปิดดูเฉย ๆ” ระหว่างทดสอบก็เปลี่ยนสถานะแล้ว

2. PUT issue ลบ Item

UpdateOrderConfirmItems ลบ Item ที่ไม่ได้ส่งมา และวนหา orderItem โดยไม่เช็ค null ก่อนใช้งาน — ถ้าส่ง Code/ExpenseId ที่ไม่มีจริงอาจได้ HTTP 500

3. FinanceId เก็บได้ค่าเดียว

ถ้า 1 Item จ่ายหลายถุง Item.FinanceId จะชี้ไปที่แถวแรกเท่านั้น ผล Lab ที่สร้างจึงผูกกับ Finance แถวแรก

4. ค้นด้วย Order No. บนหน้าจอเป็นการกรองฝั่ง Client

กรองเฉพาะรายการที่โหลดมาแล้วของ “วันที่” นั้น ถ้าใบสั่งอยู่คนละวันจะหาไม่เจอ ต้องเปลี่ยนวันที่ก่อน

5. หน้าตรวจสอบผลกรอง APPROVED เท่านั้น

ใบสั่งที่ Submit แล้วแต่ LIS ยังไม่ดึง จะไม่ปรากฏในหน้า “ตรวจสอบผล Lab”

6. ผู้ทำรายการคือเจ้าของ Token

TB_FINANCES.UserCreated = user ที่ผูกกับ PersonalToken จึงควรสร้าง service account แยกไว้ให้ตรวจสอบย้อนหลังได้

ช่องทาง Legacy (ไฟล์ ASTM + endpoint เดิม)

ก่อนจะมีชุด API ใหม่ ระบบเชื่อม BBIS ผ่าน ไฟล์ ASTM และ endpoint อีกชุดหนึ่งซึ่งยังอยู่ในโค้ด

ไฟล์ร้องขอ (Request)

MlabService.BloodBankRequest(orderId) เขียนไฟล์ {OrderId}.bld encoding TIS-620 ลงโฟลเดอร์ TBM_HOSP_PARAMETERS.BbReqPath โครงสร้าง 3 ส่วน:

H|\^&|||NOPPARAT|||||CIT5K|P||yyyyMMddHHmmss        ← Header
P|1|{LN}|{HN}|^{IDCARD}|{SURNAME}^{PRENAME}^{NAME}...  ← Patient
O|1|{LN}||^^^{LISCODE}^B^^|||||||A|||...               ← Order (1 บรรทัด/รายการ)
L|1|N                                                   ← Terminator

ทำงานเมื่อ Expense.LabMeaning = 'BB' และเป็นเคส AutoAcceptFlag

Endpoint เดิม (BloodService)

Pathหน้าที่สถานะ
GET /api/BloodBank/OrderOpd?orderNumber=ดึงใบสั่ง (อ่านจาก TB_FINANCES ตรง ๆ)ยังอยู่ในโค้ด ใช้ [Authorize] (JWT) ไม่ใช่ PersonalToken
แนะนำใช้ชุดใหม่สำหรับงานใหม่
POST /api/BloodBank/SendResultส่งผล
POST /api/BloodBank/SendCostส่งค่าใช้จ่าย
POST /api/BloodBank/SendBagแจ้งจ่ายถุง
POST /api/BloodBank/SendReturnBagแจ้งคืนถุง

ช่องว่างที่ยังไม่มีใน API ชุดใหม่

ชุดใหม่ยังไม่มี endpoint สำหรับ คืนถุงเลือด (Return Bag) และ ทิ้งถุงเลือด (Discard) แม้หน้าจอ “ตรวจสอบผล Lab” จะมีตัวกรอง RETURNED / DISCARDED อยู่แล้วก็ตาม — ปัจจุบันตัวกรองนั้นจะยังไม่คืนข้อมูล เพราะ OrderStatus ไม่เคยถูกตั้งเป็นค่าดังกล่าว
